Back to the subject at hand...

Most of the ideas people have thrown out here are things I'm thinking about. There was a lot of functionality in old-style dial-up BBS systems that is missing in these new web-based systems.

Fer instance... when I used to log into the old dial-up system, the first thing it would ask is "Check for new messages to YOU?" If you clicked YES you'd get all of the new messages since the last time you logged in that were replies to messages YOU wrote. Not just threads you'd started, but the individual messages you yourself had written.

In UBB you can't do this because replies are to a THREAD, not to an INDIVIDUAL.

Another thing you could do was a NEW MESSAGE SCAN and TOPIC SUBSCRIPTIONS. You could select what topics you were most interested in, and then scan for new messages in those topics. Anything new in those topics since the last time you READ THAT TOPIC would show up in a threaded fashion. You didn't have to scroll down a page and figure out where you left off, because the BBS knew where you left off.

There were also private messages you could send to people, you could see who else was on-line, and chat or play head-to-head games with them.

On the administrator's side, you could select how long you wanted to keep posts on-line, set maximum numbers of posts per topic, and move individual messages between topics. Lots of tasks could be automated so you never had to manually intervene in anything. (Like deleting user records of people who haven't logged on in years.)

That's the sort of system I'd like to build.

When I started my first BBS, I was the fourth user of a piece of software called the DMG BBS System, which was written by a friend of mine. It had hundreds of great features, was written in Turbo Pascal, and it came with source code.

Unfortunately, it also had some deep bugs, and once a month or so the whole thing would crash horribly, often wiping out the user database, the message database, or both at the same time. The biggest problem was that my friend wrote his own database (there were no free databases available at the time that he could use) and writing a database from scratch is hard.

After about six months of this, I decided that I really wanted to run a BBS, not write one, so I switched to QBBS. About two weeks later I heard about Remote Access, which was a QBBS clone (or possibly some ripped-off, re-engineered QBBS source code -- rumours vary). I switched to that, and used it for the next nine years.

Now totse is on the web, and the web-based BBS software I found that I liked best is UBB, but it still lacks many of the features I had with Remote Access. Most of the features that I want that it lacks can be traced directly to the fact that it uses flat files for message and user info storage, which simply do not scale well if your system has more than a few thousand messages or users.

Because of the fact that the flat files are thread-based, trying to efficiently organize messages by the user who wrote a message, or by who the message was written to, becomes a matter of synchronizing multiple flat file indexes, similar to how UBB organizes the user database. This is really hard to do well, similar in many ways to trying to write a database from scratch -- prone to errors and problems with synchronizing the various indexes. The solution is to use an off-the-shelf database, and if you do that you're pretty much locked into re-writing everything from scratch.

Which brings me back to my original dilemma -- I'd rather run a BBS than write one. If I could find software that does what I want, I'll switch. If not, I'll write my own, but I know that's a huge undertaking.
