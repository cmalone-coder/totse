Re: MySQL errors
Maybe the SQL errors are from the UBB mover accessing the database at the same time as vBulletin?

Nope. The converter only runs once a day, during the system's least-used hours in the middle of the night. After tonight's run I'm going to disable it.

I did find a couple of problems. PHP was configured to be too generous allocating time to processes, so MySQL would run out of threads.

The network card on the db server is having problems -- errors are showing up in the system message log. (I think I've fixed this with ethtool.)

MySQL was configured with some less-than-optimal settings for the size of database we have. I increased the memory allocation to better fit the size of database, but what I really need is to get more memory for the database server. I'm figuring out how much is needed right now. Looks like it's going to be somewhere in the neighborhood of 4-8GB.

Lastly, MySQL is using MyISAM tables for the database, and there are known problems with large tables stored as MyISAM files if those tables are frequently updated (lock contention problems), so I'm probably going to convert some of the key tables (posts, threads, users) over to InnoDB tables which don't have that limitation.

Re: MySQL errors
Your last logged in date was January 1, 1970 because you had never logged in to vBulletin before today, which means the database still had a default timestamp, which would be 0.

The timestamp is measured in "UNIX time", which is a count of the seconds since the UNIX epoch began, which was on January 1, 1970 at 00:00:00 GMT.

Since your log in timestamp was 0, it was the equivalent of January 1, 1970.
